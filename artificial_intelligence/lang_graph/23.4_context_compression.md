This is a good production RAG context-compression pipeline. Each stage has a distinct responsibility. I would implement it as a `DocumentCompressionService` or `RAGContextProcessor` within your LangGraph Context Engineering architecture.

Let's break down what each component does, how it is implemented in LangChain, and how the components fit together.

# 1. End-to-end architecture

01

Retrieved Documents

Retrieve top-K documents from vector and hybrid search.

02

Deduplication

Remove identical and near-duplicate documents or passages.

03

Relevance Filtering

Remove documents that are not relevant to the user query.

04

Sentence / Chunk Selection

Identify the most useful passages and sentences.

05

Compression

Extract or summarize the selected content.

06

Token Budget Validation

Measure tokens and enforce the context allocation.

07

LLM Context

Pass the final evidence to the prompt builder.

# 2. Detailed responsibilities and LangChain implementation

## Stage 1 — Retrieved Documents

Purpose: Retrieve candidate documents from your knowledge base.

Possible retrieval strategies:

- Dense vector retrieval.
- BM25 keyword retrieval.
- Hybrid retrieval.
- Metadata-filtered retrieval.
- Multi-query retrieval.
- Query decomposition.

Example:

```
retriever = vectorstore.as_retriever(    search_kwargs={"k": 30})documents = retriever.invoke(query)
```

Output: 30 candidate documents.

## Stage 2 — Deduplication

Purpose: Prevent the same information from appearing multiple times in the LLM context.

There are two types:

| Type                   | What it removes                                            |
| ---------------------- | ---------------------------------------------------------- |
| Exact deduplication    | Identical documents or text                                |
| Semantic deduplication | Different text expressing essentially the same information |

Example:

```
Document 1:
The order was delayed due to a warehouse outage.

Document 2:
The warehouse outage caused the order delay.

Document 3:
The customer requested expedited delivery.
```

Documents 1 and 2 are semantically similar.

Keep one representative passage, but preserve source references and metadata.

Implementation:

- Exact: Python hash / content hash.
- Semantic: Embeddings + cosine similarity.
- Alternative: MinHash for near-duplicate detection.

LangChain does not require you to use a particular deduplication implementation. This is often a custom document transformer.

## Stage 3 — Relevance Filtering

Purpose: Remove documents that do not answer the user's question.

Three common approaches:

| Approach                     | Implementation                                  |
| ---------------------------- | ----------------------------------------------- |
| Embedding similarity         | `EmbeddingsFilter`                              |
| LLM relevance classification | `LLMChainFilter`                                |
| Cross-encoder reranking      | Cohere Rerank, BGE Reranker, Vertex AI reranker |

Example:

```
from langchain_classic.retrievers.document_compressors import (    EmbeddingsFilter)filter = EmbeddingsFilter(    embeddings=embeddings,    similarity_threshold=0.75)filtered_docs = filter.compress_documents(    documents,    query=query)
```

For production, I would generally use a reranker before expensive LLM-based compression.

Important distinction: similarity filtering and reranking are not identical. Filtering removes candidates; reranking changes their order based on relevance.

## Stage 4 — Sentence / Chunk Selection

Purpose: Identify the specific parts of a relevant document that should enter the LLM context.

Example:

Original document:

```
Our company operates multiple warehouses.

Order 12345 was received on Monday.

The warehouse experienced a temporary outage.

The courier failed to collect the package.

We offer several payment methods.

Customers can track orders through our portal.
```

Query:

```
Why was order 12345 delayed?
```

Selected sentences:

```
Order 12345 was received on Monday.
The warehouse experienced a temporary outage.
The courier failed to collect the package.
```

Possible implementations:

- Sentence splitting + embedding similarity.
- Top-N sentence selection.
- Semantic chunking.
- LLM-based extraction.
- Sliding-window selection to preserve surrounding context.

My recommendation: Keep adjacent sentences together when they explain a cause-and-effect relationship. Selecting isolated sentences can destroy important context.

## Stage 5 — Compression

Purpose: Reduce the size of selected content while preserving useful information.

Two approaches:

A. Extractive compression

Retain original sentences without rewriting them.

```
Warehouse outage delayed order 12345.
Courier failed to collect the package.
```

B. Abstractive compression

Ask an LLM to rewrite the selected content.

```
Order 12345 was delayed because a warehouse
outage prevented the courier from collecting it.
```

LangChain components:

- `LLMChainExtractor`
- Custom LLM summarization chain.
- `DocumentCompressorPipeline`.

For evidence-heavy enterprise RAG, prefer extractive compression where possible.

## Stage 6 — Token Budget Validation

Purpose: Ensure that the assembled context fits within the available model token budget.

Example:

| Component                   | Token allocation |
| --------------------------- | ---------------- |
| System instructions         | 2,000            |
| Conversation history        | 3,000            |
| Customer memory             | 1,000            |
| Retrieved documents         | 5,000            |
| Tool results                | 2,000            |
| Response generation reserve | 2,000            |
| Total                       | 15,000           |

These are illustrative allocations.

Implementation:

```
from langchain_core.messages import trim_messagesmessages = trim_messages(    messages,    max_tokens=15000,    token_counter=model,    strategy="last",    include_system=True)
```

However, this trims messages, not individual retrieved documents.

For retrieved documents, implement a separate token-budget manager:

1. Count tokens for each document.
2. Prioritize documents by relevance.
3. Add documents until the budget is reached.
4. Preserve mandatory evidence.
5. Reject or further compress oversized content.
6. Validate the final assembled prompt.

Also reserve tokens for output and account for the model's actual context-window limit.

## Stage 7 — LLM Context

The final context is assembled into the prompt.

```
from langchain_core.prompts import ChatPromptTemplateprompt = ChatPromptTemplate.from_messages([    ("system", """    You are an enterprise customer service agent.    Answer using the supplied context.    Do not invent information.    If evidence is insufficient, say so.    Retrieved context:    {context}    """),    ("human", "{question}")])chain = prompt | llmresponse = chain.invoke({    "context": compressed_context,    "question": query})
```

# 4. Important production consideration: pipeline ordering

I would make one adjustment to your architecture:

Reranking should happen before final relevance filtering and sentence selection.

A more complete pipeline:

```
Retrieved Documents
       |
       ▼
Exact Deduplication
       |
       ▼
Semantic Deduplication
       |
       ▼
Cross-Encoder Reranking
       |
       ▼
Relevance Filtering
       |
       ▼
Sentence / Chunk Selection
       |
       ▼
Extractive / Abstractive Compression
       |
       ▼
Token Budget Management
       |
       ▼
Evidence Validation
       |
       ▼
LLM Context
```

One further detail: evidence validation should verify that compressed statements remain supported by their original source documents. Keep document IDs, chunk IDs and source metadata throughout the pipeline.

For your LangGraph architecture: This entire pipeline can be implemented as a dedicated node or subgraph, with the original retrieved documents and their provenance retained in state.

The key is to keep retrieval, compression and prompt assembly separate. This gives you independent control over latency, token consumption, retrieval quality and factual accuracy.
