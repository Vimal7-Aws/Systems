Yes. This is an **important production concern** with `Send`.

`Send` lets you create **N runtime tasks**, but you generally need to control N so an LLM or upstream system cannot accidentally create hundreds or thousands of tasks.

The key idea is:

```text
                    LLM / Input
                        │
                        ▼
                  Decompose
                        │
                        ▼
              Validate + Normalize
                        │
                        ▼
                Limit fan-out
                        │
                        ▼
                   Send(...)
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
         W1            W2            W3
```

## 1. Hard maximum — simplest protection

For example, allow at most 10 subqueries:

```python
MAX_SUBQUERIES = 10

def fan_out(state):

    queries = state["sub_queries"]

    queries = queries[:MAX_SUBQUERIES]

    return [
        Send("search_worker", {"query": q})
        for q in queries
    ]
```

If the LLM returns:

```text
Q1 ... Q25
```

only:

```text
Q1 ... Q10
```

are dispatched.

This should usually be your **first safety boundary**.

---

# 2. Validate before `Send`

Don't directly trust the LLM output.

Use:

```text
LLM
 ↓
Structured output
 ↓
Validation
 ↓
Deduplication
 ↓
Maximum
 ↓
Send
```

For example:

```python
def prepare_queries(state):

    queries = state["sub_queries"]

    # Remove empty queries
    queries = [
        q.strip()
        for q in queries
        if q and q.strip()
    ]

    # Deduplicate
    queries = list(dict.fromkeys(queries))

    # Hard limit
    queries = queries[:10]

    return {
        "sub_queries": queries
    }
```

Then:

```python
def fan_out(state):

    return [
        Send("search_worker", {"query": q})
        for q in state["sub_queries"]
    ]
```

This gives you:

```text
               LLM
                │
                ▼
        [25 subqueries]
                │
                ▼
          Validation
                │
                ▼
          Deduplication
                │
                ▼
            Limit 10
                │
                ▼
           Send × 10
```

---

# 3. Don't confuse task count with concurrency

This is **very important**.

Suppose:

```python
return [
    Send("worker", {"item": item})
    for item in items
]
```

and there are:

```text
100 items
```

You have created **100 logical work items**.

That is different from saying:

> "I want 100 external API calls simultaneously."

You need to distinguish:

```text
Fan-out size
      ↓
How many tasks exist?

Concurrency
      ↓
How many tasks execute at once?
```

For example:

```text
100 tasks
   │
   ├── 10 executing
   ├── 90 waiting/queued
   │
   ▼
External service
```

That is generally much safer than allowing uncontrolled concurrency.

---

# 4. Control fan-out at multiple layers

For production, I would use **four layers of protection**:

```text
             User / LLM
                  │
                  ▼
        1. Maximum task count
                  │
                  ▼
        2. Task validation
                  │
                  ▼
        3. Concurrency control
                  │
                  ▼
        4. External API limits
```

For example:

```text
MAX_SUBQUERIES = 10

MAX_CONCURRENT_RETRIEVALS = 5

VECTOR_DB_RATE_LIMIT = X

LLM_RATE_LIMIT = Y
```

These solve different problems.

---

# 5. Limit based on query complexity

You don't necessarily need the same fan-out for every request.

For example:

```text
Simple query
   → max 3

Normal query
   → max 5

Complex query
   → max 10
```

Conceptually:

```python
def calculate_limit(state):

    if state["complexity"] == "simple":
        return 3

    if state["complexity"] == "normal":
        return 5

    return 10
```

Then:

```python
def fan_out(state):

    limit = calculate_limit(state)

    queries = state["sub_queries"][:limit]

    return [
        Send(
            "search_worker",
            {"query": q}
        )
        for q in queries
    ]
```

This prevents expensive requests from exploding.

---

# 6. Deduplicate before fan-out

This is particularly useful for LLM-generated queries.

Suppose the model generates:

```text
What is HNSW?
Explain HNSW
What is HNSW?
HNSW algorithm
Explain HNSW algorithm
```

You don't want:

```text
5 retrieval tasks
```

when there may only be:

```text
2-3 meaningful searches
```

So:

```python
queries = list(dict.fromkeys(queries))
```

before `Send`.

For semantic duplicates, you could use query normalization or a similarity-based deduplication step.

# 7. Priority-based fan-out

A more sophisticated architecture is:

```text
LLM
 ↓
20 candidate queries
 ↓
Score / prioritize
 ↓
Top 5
 ↓
Send
```

For example:

```python
queries = sorted(
    state["sub_queries"],
    key=lambda q: q["priority"],
    reverse=True
)

queries = queries[:5]
```

Then only the most important tasks are dispatched.

This is useful when the LLM produces more candidate work than your infrastructure budget allows.

---

# 8. Budget-based fan-out

This is even more architecturally interesting.

Instead of only asking:

> How many tasks?

ask:

> How much work can this request afford?

For example:

```text
Request budget = 100 units

Task 1 = 10
Task 2 = 20
Task 3 = 15
Task 4 = 30
Task 5 = 40
```

You could dispatch only tasks whose total estimated cost fits within the budget.

```text
Budget
  │
  ▼
Task selection
  │
  ├── Q1 = 10 ✓
  ├── Q2 = 20 ✓
  ├── Q3 = 15 ✓
  ├── Q4 = 30 ✓
  └── Q5 = 40 ✗
```

This is particularly useful for expensive:

* LLM calls
* reranking
* web searches
* external APIs
* multi-agent workflows

---

# 9. Control fan-out based on downstream capacity

This is one of the most important production concepts.

Suppose your graph does:

```text
Send
 ↓
AstraDB
 ↓
Vertex reranker
 ↓
Gemini
```

You shouldn't determine fan-out independently of those systems.

For example:

```text
Graph
  │
  ▼
10 concurrent workers
  │
  ▼
AstraDB
  │
  ▼
10 reranker calls
  │
  ▼
10 LLM calls
```

The bottleneck might actually be:

```text
Vertex API
```

So your architecture should be designed around the **capacity of the constrained downstream dependency**.

---

# 10. Use a bounded worker pattern

Conceptually, think:

```text
                  Send
                    │
             100 logical tasks
                    │
                    ▼
              Worker pool
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
      W1            W2           W3
       │            │            │
       └────────────┼────────────┘
                    │
              max concurrency
                    │
                    ▼
                Vector DB
```

For example:

```text
100 tasks
     ↓
max 5 concurrent
     ↓
Vector DB
```

This is fundamentally different from limiting the task count to 5.

You might have:

```text
100 tasks
5 concurrent
```

rather than:

```text
5 tasks total
```

The exact mechanism for enforcing bounded concurrency depends on your LangGraph/runtime deployment and the downstream service; `Send` itself is the fan-out mechanism, not a general-purpose semaphore.

---

# 11. Backpressure

This leads to an important distributed-systems concept:

**backpressure**.

Suppose:

```text
LLM generates 100 tasks
        ↓
Graph
        ↓
Vector DB can safely handle 5 at a time
```

You don't want:

```text
100
 ↓
100 simultaneous requests
 ↓
Vector DB overloaded
```

Instead:

```text
100 tasks
   ↓
bounded execution
   ↓
5 at a time
   ↓
Vector DB
```

This is the same architectural principle you see in:

* Kafka consumers
* worker pools
* Kubernetes workloads
* async task queues
* database connection pools
* API rate limiting

---

# 12. Nested fan-out needs special care

Remember the example:

```text
3 queries
 ×
3 retrieval strategies
 =
9 tasks
```

Now imagine:

```text
10 queries
 ×
5 retrieval methods
 ×
2 agents
 =
100 executions
```

And retries:

```text
100
 ×
up to 3 attempts
=
300 executions
```

So at architecture level, you need to calculate the **fan-out multiplication factor**.

```text
Total potential work
≈
N
×
branch factor
×
retry factor
```

This is one of the most important things to consider when designing complex LangGraph systems.

# 13. Put a limit at every fan-out boundary

For a complex graph:

```text
                    Planner
                       │
                    Send × N
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
            Agent     Agent    Agent
              │        │        │
           Send × M  Send × M Send × M
              │        │        │
              ▼        ▼        ▼
            Tools    Tools    Tools
```

Don't only protect the first `Send`.

Think:

```text
Planner fan-out
      ↓
Agent fan-out
      ↓
Tool fan-out
```

Each layer should have appropriate limits.

# 15. A particularly important distinction

There are **three different controls**:

| Control           | Question                                                |
| ----------------- | ------------------------------------------------------- |
| Fan-out limit     | How many tasks may I create?                            |
| Concurrency limit | How many tasks may execute simultaneously?              |
| Rate limit        | How many requests may I send to a dependency over time? |

For example:

```text
Fan-out = 50
Concurrency = 5
Rate = 20 requests/sec
```

means conceptually:

```text
50 logical tasks
      ↓
5 executing concurrently
      ↓
dependency receives ≤ 20 req/sec
```

These controls should not be conflated.

# 16. The architect-level pattern

For your LangGraph/RAG architecture, I'd remember:

```text
                  LLM
                   │
                   ▼
             Generate tasks
                   │
                   ▼
          ┌──────────────────┐
          │ Validate         │
          │ Deduplicate      │
          │ Prioritize       │
          │ Limit N          │
          └────────┬─────────┘
                   │
                   ▼
                 Send
                   │
            N logical tasks
                   │
                   ▼
          Bounded concurrency
                   │
                   ▼
          External dependencies
                   │
                   ▼
               Reducer
                   │
                   ▼
              Aggregation
```

So the answer to **"How do I control dynamic fan-out?"** is not just:

```python
queries[:10]
```

That's only the first layer.

For a production-grade system, think:

> **Validate → Deduplicate → Limit task count → Prioritize/budget → Bound concurrency → Rate-limit dependencies → Retry carefully → Aggregate with reducers.**

That is the architecture I would use for your **Decompose → Send → parallel retrieval → rerank → merge** RAG design.
