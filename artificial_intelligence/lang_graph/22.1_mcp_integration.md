# PART 22 — MCP + LangGraph: Complete Production Engineering Tutorial

This is a particularly important topic for your AI Engineer / AI Architect learning path because MCP provides the standardized tool integration layer, while LangGraph provides the agent orchestration and execution layer.

You should understand both independently and, more importantly, how to combine them in a production enterprise architecture.

Given your work with FastMCP, Python, remote Streamable HTTP servers, Google Cloud Run, Vertex AI and LangGraph, I'll use those technologies in the examples.

# 1. Understanding the MCP + LangGraph architecture

First, understand the responsibilities of each component.

Application Layer

Web UI / Mobile App / Enterprise API

LangGraph Agent Runtime

State · Nodes · Edges · Router · Memory · Checkpointing

MCP Client / Adapter Layer

Discovery · Schema conversion · Authentication · Transport

Database

Postgres, Redis

APIs

REST, internal APIs

SaaS

Salesforce, Jira

### What does each layer do?

| Component      | Responsibility                       |
| -------------- | ------------------------------------ |
| LangGraph      | Controls agent workflow              |
| LLM            | Decides which tool to invoke         |
| MCP client     | Connects to MCP servers              |
| MCP server     | Exposes capabilities                 |
| MCP tools      | Perform specific operations          |
| Authentication | Establishes identity and permissions |
| Checkpointer   | Persists graph execution state       |
| Observability  | Tracks model and tool execution      |

Important distinction:

MCP does not replace LangGraph tools, and LangGraph does not replace MCP.

MCP standardizes how external capabilities are exposed and accessed. LangGraph decides when and how those capabilities are used.

# 2. MCP tools as LangGraph agent tools

This is the first mandatory concept.

An MCP server exposes tools using the MCP protocol.

For example, imagine your FastMCP server exposes:

```
@mcp.tool()def get_customer(customer_id: str):    """Retrieve customer information."""    return {        "customer_id": customer_id,        "name": "John",        "status": "ACTIVE"    }
```

The MCP server exposes a tool definition containing:

- Tool name
- Description
- Input schema
- Tool execution capability

LangGraph needs to convert or adapt this MCP tool into a tool interface that its model can invoke.

The LangChain MCP adapter provides this integration.

### Architecture

```
MCP Server
    |
    | tools/list
    v
MCP Client
    |
    | Convert MCP tool definitions
    v
LangChain BaseTool
    |
    v
LLM Tool Binding
    |
    v
LangGraph ToolNode
    |
    v
MCP Tool Execution
```

### Production-style Python example

Install:

```
pip install \
    langgraph \
    langchain \
    langchain-mcp-adapters \
    langchain-google-genai
```

Create an MCP client:

```
from langchain_mcp_adapters.client import (    MultiServerMCPClient)client = MultiServerMCPClient(    {        "customer_service": {            "transport": "streamable_http",            "url": "https://customer-mcp.example.com/mcp",        }    })
```

Discover tools:

```
tools = await client.get_tools()for tool in tools:    print(tool.name)    print(tool.description)    print(tool.args_schema)
```

This retrieves the available tools from the MCP server and adapts them into LangChain-compatible tools.

Now bind them to an LLM:

```
from langchain_google_genai import ChatGoogleGenerativeAIllm = ChatGoogleGenerativeAI(    model="gemini-2.5-flash",    temperature=0)llm_with_tools = llm.bind_tools(tools)
```

Create a LangGraph workflow:

```
from langgraph.prebuilt import (    create_react_agent)agent = create_react_agent(    model=llm,    tools=tools)
```

Execute:

```
result = await agent.ainvoke(    {        "messages": [            {                "role": "user",                "content": "Get customer C1001"            }        ]    })print(result["messages"][-1].content)
```

The important thing to understand is that the MCP tools are now available to the agent through the LangChain tool abstraction.

The agent does not need to know the underlying database or API implementation.

Note: This is a simplified integration example. In production, add explicit lifecycle management, authentication, authorization, execution limits and error handling. Adapter APIs can differ between package versions.

# 3. MCP server discovery

Discovery is one of the most important MCP concepts.

Imagine you have five remote MCP servers:

| MCP server    | Tools                           |
| ------------- | ------------------------------- |
| Customer MCP  | get_customer, update_customer   |
| Order MCP     | get_order, cancel_order         |
| Payment MCP   | process_payment, refund_payment |
| Inventory MCP | check_stock, reserve_stock      |
| Shipping MCP  | track_shipment                  |

How does LangGraph know which tools are available?

Through MCP discovery.

### MCP discovery lifecycle

```
LangGraph Application
        |
        v
     MCP Client
        |
        v
  Initialize Connection
        |
        v
  MCP Server Response
        |
        v
   tools/list
        |
        v
  Tool Definitions
        |
        v
  Schema Conversion
        |
        v
  LangGraph Agent
```

The MCP protocol provides methods including:

- `initialize`
- `tools/list`
- `tools/call`
- `resources/list`
- `resources/read`
- `prompts/list`
- `prompts/get`

These are protocol-level operations.

### Static versus dynamic discovery

Static discovery

You configure the servers at application startup.

```
client = MultiServerMCPClient({    "customer": {        "transport": "streamable_http",        "url": CUSTOMER_MCP_URL    },    "orders": {        "transport": "streamable_http",        "url": ORDER_MCP_URL    }})
```

Advantages:

- Predictable tool inventory.
- Easier governance.
- Easier deployment.
- Lower discovery overhead.

Dynamic discovery

The application discovers servers and their capabilities dynamically.

Useful when:

- You have many MCP servers.
- Different tenants have different capabilities.
- Tools are registered through an enterprise tool registry.
- Tools change independently of the agent deployment.

Production recommendation: use a controlled MCP server registry rather than allowing an LLM to discover and connect to arbitrary MCP endpoints.

# 4. MCP tool schemas

This is especially important for reliable tool calling.

Consider this tool:

```
@mcp.tool()def transfer_money(    source_account: str,    destination_account: str,    amount: float):    ...
```

The MCP server exposes an input schema.

Conceptually:

```
{
  "type": "object",
  "properties": {
    "source_account": {
      "type": "string"
    },
    "destination_account": {
      "type": "string"
    },
    "amount": {
      "type": "number"
    }
  },
  "required": [
    "source_account",
    "destination_account",
    "amount"
  ]
}
```

The LLM uses this schema to construct tool arguments.

### What should an AI architect understand?

1. JSON Schema validation.
2. Required versus optional fields.
3. Enum constraints.
4. Nested objects.
5. Array validation.
6. Schema versioning.
7. Backward compatibility.
8. Invalid tool arguments.
9. Tool description quality.
10. Input sanitization.

Important: A valid tool schema does not mean the requested operation is authorized.

For example, an LLM may generate:

```
{
  "source_account": "A100",
  "destination_account": "A200",
  "amount": 1000000
}
```

The schema might be perfectly valid, but the user might not have permission to transfer that amount.

Business validation and authorization must happen independently on the MCP server or downstream service.

This is one of the most important enterprise topics.

You need to establish identity at multiple boundaries.

### Authentication mechanisms

| Mechanism       | Usage                                             |
| --------------- | ------------------------------------------------- |
| OAuth 2.0       | User/delegated authorization                      |
| OAuth 2.1       | Modern OAuth-based MCP authorization profile      |
| JWT             | Identity and claims                               |
| Service account | Workload identity                                 |
| API keys        | Service authentication in controlled environments |
| mTLS            | Mutual service authentication                     |
| IAM             | Cloud resource access control                     |

### The critical distinction: user identity versus service identity

Suppose Alice logs in and asks:

"Show me customer C1001."

Your LangGraph application runs under a Cloud Run service account.

There are two different identities:

- Alice: the end-user identity.
- LangGraph service account: the workload identity.

You must decide whether the MCP server should authorize using Alice's delegated identity, the workload identity, or both.

For sensitive customer operations, simply forwarding the Cloud Run service account identity may not be enough.

### Recommended enterprise flow

```

        |
        v

        |

        |

  LangGraph Runtime
        |
        v
  Token Validation
        |
        v
  MCP Client
        |
        v
  MCP Server
        |
        v
  Authorization Check
        |
        v
  Database / API
```

Do not blindly forward the incoming user token to every MCP server.

Use audience-specific tokens and an appropriate OAuth token exchange/delegation design where required.

For Google Cloud, investigate:

- Cloud Run service identity.
- Workload Identity.
- IAM service-to-service authentication.
- OAuth token exchange.
- Secret Manager.
- Identity-Aware Proxy where appropriate.

# 6. MCP transport mechanisms

MCP transport determines how the client and server communicate.

You should understand the differences between the transport mechanisms.

| Transport       | Purpose                     | Typical usage         |
| --------------- | --------------------------- | --------------------- |
| stdio           | Local process communication | Local development     |
| Streamable HTTP | Remote MCP communication    | Production remote MCP |
| HTTP with SSE   | Legacy transport            | Older MCP deployments |

### A. stdio

```
LangGraph Process
       |
       v
  MCP Client
       |
       v
   Subprocess
       |
       v
   MCP Server
```

Useful for:

- Local development.
- Desktop integrations.
- Locally managed tools.

Not generally the right choice for independently deployed remote MCP services.

### B. Streamable HTTP

```
LangGraph on Cloud Run
        |
        | HTTPS
        v
  MCP Server on Cloud Run
        |
        v
   Internal Services
```

This is the transport I would focus on for your architecture.

It supports remote communication through HTTP, with streaming capabilities where needed.

Important concepts:

- HTTP POST requests.
- Optional HTTP GET for server-initiated streams.
- JSON-RPC messages.
- Session management where applicable.
- Authentication headers.
- Request correlation.
- Streaming responses.
- Connection lifecycle.

Do not confuse Streamable HTTP with the older HTTP+SSE transport.

### Important design decision

I would not create a new MCP connection for every tool call.

Instead, manage MCP client connections and their lifecycle appropriately.

However, distinguish connection reuse from session reuse: the MCP client adapter's lifecycle and session semantics depend on the transport and library version.

Also, do not assume that every MCP tool invocation requires a separate LLM call.

A typical ReAct execution may involve:

1. One LLM call to decide which tools to invoke.
2. One or more tool executions.
3. Another LLM call to interpret tool results.

If the LLM requests multiple tools in one response, they may be executed together depending on the graph and tool-node configuration.

# 8. MCP failure handling

Production systems must expect MCP failures.

Consider these scenarios:

| Failure                | Example                | Recommended response        |
| ---------------------- | ---------------------- | --------------------------- |
| Connection failure     | MCP server unavailable | Retry with backoff          |
| Timeout                | Tool takes too long    | Enforce deadline            |
| Authentication failure | Expired token          | Refresh or re-authenticate  |
| Authorization failure  | User lacks permission  | Fail closed                 |
| Invalid schema         | Missing argument       | Validate and return error   |
| Tool exception         | Database error         | Map to safe error           |
| Rate limiting          | HTTP 429               | Respect Retry-After         |
| Server error           | HTTP 500               | Controlled retry            |
| Session failure        | Invalid session        | Reinitialize if appropriate |
| Network interruption   | Connection dropped     | Retry only if safe          |

### Retry strategy

Use exponential backoff with jitter.

Example:

```
import asyncioimport randomasync def retry_operation(    operation,    max_attempts=3):    for attempt in range(max_attempts):        try:            return await operation()        except (TimeoutError, ConnectionError):            if attempt == max_attempts - 1:                raise            delay = (                2 ** attempt                + random.uniform(0, 0.5)            )            await asyncio.sleep(delay)
```

This is a simplified example. In production, classify errors by retryability, enforce an overall deadline, and use bounded retries.

Never blindly retry financial transactions or other non-idempotent operations.

For those operations, use:

- Idempotency keys.
- Transaction identifiers.
- Duplicate request detection.
- Operation status reconciliation.
- Explicit compensation workflows.

# 9. MCP timeouts and circuit breakers

You need to understand three different controls.

Timeout: How long are you willing to wait for one operation?

Retry: Should you try the operation again?

Circuit breaker: Should you temporarily stop calling a failing service?

Example:

```
          MCP Client
               |
               v
        Circuit Breaker
               |
        +------+------+
        |             |
      CLOSED        OPEN
        |             |
        v             v
   Call MCP       Reject Fast
        |
        v
     Timeout
        |
        v
     Retry
```

Circuit breaker states:

| State     | Meaning                       |
| --------- | ----------------------------- |
| CLOSED    | Requests flow normally        |
| OPEN      | Requests are rejected         |
| HALF_OPEN | Limited test requests allowed |

For production, configure separate policies for each MCP server.

For example:

- Customer MCP: 3-second timeout.
- Inventory MCP: 2-second timeout.
- Payment MCP: 5-second timeout.

These are illustrative values, not universal defaults. Set them based on service-level objectives and measured latency.

# 10. MCP security

This deserves particular attention because MCP gives an agent access to external capabilities.

Understand these security categories.

### A. Authentication

Who is connecting?

### B. Authorization

What can that identity do?

### C. Tool-level permissions

Can the agent call `get_customer` but not `delete_customer`?

### D. Input validation

Can malicious arguments reach downstream systems?

### E. Prompt injection

Can an external tool response manipulate the agent?

### F. Data exfiltration

Can the agent send confidential information to an unauthorized tool?

### G. SSRF and endpoint security

Can an attacker persuade your system to connect to an arbitrary MCP endpoint?

### H. Auditability

Can you reconstruct exactly which user invoked which tool and what happened?

### Security architecture

```
               User Request
                    |
                    v
             Identity Check
                    |
                    v
             LangGraph Agent
                    |
                    v
              Tool Policy
                    |
                    v
           MCP Authentication
                    |
                    v
           MCP Authorization
                    |
                    v
             Input Validation
                    |
                    v
              Tool Execution
                    |
                    v
             Output Filtering
                    |
                    v

```

### Security controls to implement

| Security control  | Implementation                         |
| ----------------- | -------------------------------------- |
| Tool allowlisting | Registered tool catalogue              |
| Least privilege   | Per-tool permissions                   |
| Tenant isolation  | Tenant identity propagation            |
| Secret management | Secret Manager                         |
| Token validation  | Issuer, audience, expiry               |

The LLM must never be the security enforcement mechanism.

# 11. HITL around MCP tools

Human-in-the-loop becomes important when agents perform operations that have consequences.

For example:

| Tool            | HITL requirement                    |
| --------------- | ----------------------------------- |
| get_customer    | Usually unnecessary                 |
| get_order       | Usually unnecessary                 |
| update_address  | Depending on policy                 |
| cancel_order    | Potentially required                |
| refund_payment  | Required above configured threshold |
| transfer_money  | Strong approval required            |
| delete_customer | Strong approval required            |

### LangGraph architecture

```
             User Request
                  |
                  v
             LangGraph
                  |
                  v
             Tool Decision
                  |
                  v
           Sensitive Operation?
              /        \
            No          Yes
            |            |
            v            v
         Execute       Interrupt
            |            |
            |            v
            |        Human Review
            |            |
            |       +----+----+
            |       |         |
            |     Approve    Reject
            |       |         |
            |       v         v
            |    Execute    Stop
            |       |
            +-------+
                  |
                  v
              Final Result
```

### Example with LangGraph

LangGraph provides interrupt and resume capabilities.

```
from langgraph.types import interruptfrom langgraph.prebuilt import ToolNodedef approval_node(state):    decision = interrupt({        "action": "refund_payment",        "amount": state["amount"],        "reason": state["reason"],        "message": "Approve this refund?"    })    if not decision["approved"]:        return {            "status": "rejected"        }    return {        "approved": True    }
```

You would then route to the payment execution node only when approval is granted.

To resume, use the same thread identifier and a `Command(resume=...)` payload.

Important production considerations:

- Persist graph checkpoints.
- Associate approvals with the authenticated user.
- Bind approval to the exact operation and arguments.
- Expire old approvals.
- Prevent replay.
- Revalidate authorization immediately before execution.
- Never allow the model to manufacture an approval.

# 12. MCP server versioning and tool governance

This is an important AI architect topic that is often overlooked.

Imagine you have:

```
customer-mcp-v1
customer-mcp-v2
customer-mcp-v3
```

Version 1 exposes:

```
get_customer(customer_id)
```

Version 2 exposes:

```
get_customer(    customer_id,    include_orders=False)
```

Version 3 changes the output schema.

How do you avoid breaking production agents?

You need a tool governance strategy.

Recommended architecture:

```
             MCP Registry
                  |
       +----------+----------+
       |          |          |
       v          v          v
  Customer V1 Customer V2 Order V1
       |          |          |
       +----------+----------+
                  |
             Tool Catalogue
                  |
                  v
             LangGraph
```

Track:

- Server name.
- Server version.
- Tool name.
- Tool schema version.
- Tool description.
- Authentication requirements.
- Authorization policy.
- Compatibility status.
- Deprecation date.
- Owner.
- Health status.

Do not treat an MCP tool's name as a complete versioning strategy.

For incompatible schema changes, consider a new tool name or an explicitly versioned server/tool contract.

# 15. Advanced topic: Dynamic MCP tool selection

This is where MCP and LangGraph become particularly interesting.

Imagine you have 100 MCP tools across 20 servers.

Should you expose all 100 tools to Gemini for every request?

Usually, no.

Why?

- Larger tool-selection context.
- More ambiguous tool choices.
- Increased token usage.
- Potentially higher latency.
- Larger security exposure.

Instead, introduce a tool-selection architecture.

```
              User Query
                  |
                  v
             Intent Router
                  |
       +----------+----------+
       |          |          |
       v          v          v
    Customer    Orders     Payments
      MCP        MCP         MCP
       |          |          |
       v          v          v
   Relevant    Relevant    Relevant
    Tools       Tools       Tools
       |          |          |
       +----------+----------+
                  |
                  v
             LLM Agent
                  |
                  v
             Tool Execution
```

Possible approaches:

1. Static tool allowlisting.
2. Intent-based routing.
3. Server-level tool discovery.
4. Semantic tool search.
5. Hierarchical tool registries.
6. Dynamic tool binding.

For an enterprise architecture, I would favour a hybrid approach:

- Static server registry.
- Dynamic capability discovery.
- Intent-based tool selection.
- Tenant-specific authorization.
- Per-request tool allowlisting.

This gives you flexibility without allowing arbitrary tool access.

# 18. Advanced topic: MCP versus direct API integration

An AI architect should know when MCP is appropriate and when a direct integration is better.

| Criteria                    | MCP                                      | Direct API            |
| --------------------------- | ---------------------------------------- | --------------------- |
| Standardized tool interface | Yes                                      | Not inherently        |
| Tool discovery              | Built into protocol                      | Usually custom        |
| Cross-client reuse          | Strong                                   | Requires adapters     |
| Existing REST integration   | Requires MCP wrapper                     | Direct                |
| Agent integration           | Natural with adapters                    | Requires tool wrapper |
| Protocol overhead           | Additional layer                         | Usually lower         |
| Governance                  | Centralized capability contract possible | Custom                |
| Streaming                   | Supported by Streamable HTTP             | Depends on API        |

My recommendation:

Use MCP when capabilities need to be standardized and reused across multiple agents, applications or AI clients.

Use direct APIs when a simple, tightly controlled application integration is sufficient.

You can also use both within the same LangGraph system.
