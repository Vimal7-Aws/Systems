Yes — **when you compile a LangGraph graph with a checkpointer, checkpointing is automatic.** You normally do **not** call `checkpointer.save()` after every node.

Conceptually:

```text
graph.invoke()
      │
      ▼
   Node A
      │
      ▼
 checkpoint ───────► PostgreSQL
      │
      ▼
   Node B
      │
      ▼
 checkpoint ───────► PostgreSQL
      │
      ▼
   Node C
      │
      ▼
 checkpoint ───────► PostgreSQL
      │
      ▼
    END
```

### Example

```python
checkpointer = PostgresSaver(pool)

graph = builder.compile(
    checkpointer=checkpointer
)

config = {
    "configurable": {
        "thread_id": "user-123"
    }
}

result = graph.invoke(
    {"question": "What is RAG?"},
    config=config
)
```

You don't do:

```python
# ❌ Normally you don't do this
checkpointer.save(state)
```

LangGraph's execution/runtime manages checkpoint creation through the configured checkpointer.

### What gets checkpointed?

It's not simply:

```text
Node A output → database
Node B output → database
```

The checkpoint represents the **graph's execution state** at a particular point, including state/channel information and execution metadata needed for durable execution and resumption.

For example:

```text
thread_id = "user-123"

Checkpoint 1
    state after Node A
    next = ["B"]

Checkpoint 2
    state after Node B
    next = ["C"]

Checkpoint 3
    state after Node C
    next = []
```

### Why this matters

Suppose:

```text
Node A
   ↓
checkpoint
   ↓
Node B
   ↓
checkpoint
   ↓
Node C
   💥 failure
```

When the workflow is resumed, LangGraph has durable state from the previous checkpoints instead of relying on the memory of the crashed Cloud Run instance.

---

### One important nuance

Don't think of the rule as strictly:

> **"one database checkpoint after every Python node function."**

LangGraph's checkpointing occurs at **graph execution boundaries/supersteps**, and the exact behavior matters particularly when you have:

* parallel nodes
* `Send`
* subgraphs
* interrupts
* retries
* conditional routing

For example:

```text
                 ┌── Retriever A ──┐
                 │                 │
START → Router ──┼── Retriever B ──┼──► Merge
                 │                 │
                 └── Retriever C ──┘
```

The state produced by parallel execution is handled according to LangGraph's state/reducer and checkpoint semantics; it's not simply three independent database commits that you manually manage.

### Architect mental model

Think of it as:

```text
You define:

StateGraph
    +
Nodes
    +
Edges
    +
Checkpointer

             ↓

LangGraph runtime manages:

execution
   +
state transitions
   +
checkpoint creation
   +
persistence
   +
resume
   +
replay
```

So your application code focuses on **business logic**, while the LangGraph runtime handles the durable execution machinery.

For your Cloud Run architecture, this is particularly valuable because Cloud Run instances are disposable:

```text
Cloud Run instance
       │
       ▼
LangGraph runtime
       │
       ├── Node A
       │
       ├── checkpoint ──► Cloud SQL
       │
       ├── Node B
       │
       └── checkpoint ──► Cloud SQL
```

If the instance disappears, another instance can use the persisted checkpoint for the same `thread_id`.

The next concept you should understand is **what exactly happens when Node C fails after Node A and B have already checkpointed**—especially **resume vs retry vs replay**, because that's where LangGraph's durable execution model becomes really important.
